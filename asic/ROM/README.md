# ROM boot_rom_2048x32 - DRC problem notes

A simple explanation of why the OpenRAM-generated boot ROM has DRC errors,
what we tried so far, and where we stand. (Last updated: 2026-11-14)

---

## 1. What is this?

- `boot_rom_2048x32` = the PULP boot ROM: 2048 words x 32 bits (8 KB).
- It was generated by **OpenRAM** (ROM compiler, sky130 technology, stable branch).
- Like every OpenRAM macro, OpenRAM itself runs a DRC check after generating it.
  Its result: **1984 DRC errors** (Magic counting).

DRC ("Design Rule Check") = the foundry's geometric rules. Example:
"two pieces of metal/implant must be at least X um apart". If a shape is drawn
too close to another shape, that spot is one DRC error.

---

## 2. Why do the errors happen? (plain language)

The errors are **not random**. They come from a handful of *systematic* drawing
mistakes inside OpenRAM's ROM cells - the same mistake repeats on every column
or every row, which is why the counts are big round numbers.

Think of the memory as a big grid: the bitcell array in the middle, and helper
circuits around it (precharge on top, row decoder on the side, bitline
inverters below the array, etc.). The helper circuits are placed *next to* the
array, and several of them are placed **too close** to the array or to each
other:

| # | Where | What is drawn wrong | Rule name | Count (KLayout) |
|---|-------|--------------------|-----------|-----------------|
| 1 | Implants (nsdm/psdm) everywhere | Small gaps between implant shapes, and implant strips that are a hair too thin (0.26 vs 0.38 um) | `nsdm.1`, `psdm.1` | ~199,000 |
| 2 | Bitline inverter vs precharge row | The inverter is placed too close to the array: its poly-contact "npc" marker overlaps the precharge cell's tap contact, and two contacts end up only 0.15 um apart (0.17 needed) | `licon.13_a`, `MR_licon.SP.1`, `li.3` | 256 + 257 + 512 |
| 3 | Row decoder vs bitcell rows | Decoder diffusion/taps too close to each other and to the array (needs 0.27 / 0.38 um) | `difftap.3`, `nsdm.1` | 2048 + 512 |
| 4 | Precharge array internals | Tiny 0.08 um nwell notches between the array nwell and each cell's nwell | `nwell.2a` | 262 |
| 5 | Periphery m1 straps | Two parallel metal-1 wires only 0.105 um apart (0.14 needed) | `m1.2` | 74 |

Why does fixing matter? Same reason as the SRAM: a macro that is not DRC-clean
cannot be signed off, and it can cause real manufacturing problems.

Note: KLayout counts 202,793 "errors" where Magic counts 1,984. Same layout,
different counting style (KLayout reports each violating shape pair; Magic
groups them into tiles). We use KLayout for the per-rule breakdown because it
tells us exactly which rule fails and where.

---

## 3. What we tried so far

### Step 1 - gap fill script (copied from the SRAM work) - WORKS
`SRAM_32x1024_v2` had the same implant-gap problem and reached **0 errors** by
growing a script (`gap_fill.py`) that fills tiny gaps between implant shapes
safely (it never touches transistors - it keeps away from the diffusion).

For the ROM we copied it as **`rom_gap_fill.py` + `rom_gap_fill.sh`** (in this
folder, tested on a throwaway copy in /tmp - the original GDS is never
touched):

```
nsdm.1   188,613 ->   518      (99.7% fixed)
psdm.1    10,747 ->     0      (100% fixed)
nwell.2a     262 ->     0      (with FILL_NWELL=1, proven safe here)
total     202,793 -> 3,689
```

It does **not** fix the contact/diffusion/metal rules (see below) because for
those, filling the gap would merge shapes that carry *different signals*
(short circuits) or change transistors.

### Step 2 - "maybe the OpenRAM dev branch already fixed it?" - NO
We cloned the dev branch into a separate folder (`~/OpenRAM_dev_test`,
`~/OpenRAM` stable untouched). Findings:

- The ROM cell drawing code is **identical** between stable and dev.
- The OpenRAM maintainer himself marked the ROM compiler as broken on dev
  (commit Oct 2026: "The ROM compiler is not functional", sky130 ROM tests
  fail DRC, one test alone reports 3,674 errors).
- Verdict: switching branches would not help. We stay on stable.

### Step 3 - find the real root cause - DONE
Using the KLayout DRC report we traced every remaining error class to the
exact cell and coordinates, then read the OpenRAM python code that draws it.
Result: each error class is one systematic placement/drawing bug in the
generator (see table in section 2).

### Step 4 - fix the generator (path 1) - FIRST FIX DONE, VERIFIED
The first and clearest bug: the **bitline inverter array placed too close** to
the precharge row of the memory array.

Fix (one line, already applied to `~/OpenRAM/compiler/modules/rom_bank.py`):

```
inv_y_offset = ... - 1.5 * m1_pitch   ->   ... - 2.0 * m1_pitch
```

Why 2.0? Moving it further (2.5/7.5) removes the contact errors too but then
the inverter's n-well no longer overlaps the array's n-well - and the inverter
has no well tap of its own, so that overlap is what connects its well to vdd.
More clearance = DRC clean but **LVS broken** (we tested and saw it fail).
2.0 is the verified sweet spot: contacts fixed AND well still connected.

Verified on a fast 64-word test ROM (builds in ~11 s instead of ~35 min):

| Rule            | before | after |
|-----------------|--------|-------|
| licon.13_a      | 256    | 0     |
| MR_licon.SP.1   | 257    | 0     |
| li.3            | 512    | 0     |
| nwell.2a        | 7      | 7 (unchanged) |
| LVS             | pass   | pass  |

### Step 5 - row decoder fix - DONE, VERIFIED
The row/column decoders are `rom_base_array`s filled with the same ROM cells.
Two problem classes there:

1. **`difftap.3` (24 in tiny / 2048+ in big)** - every strap column of active
   taps sits only 0.23-0.265 um from the ROM cell's diffusion (needs 0.27).
   Fix: the decode arrays now pass `tap_extra_offset=0.06` to
   `rom_base_array`, which shifts the active-tap diffusion 0.06 um right
   inside `rom_poly_tap` (`extra_tap_offset`). The precharge array's taps do
   NOT get the shift (shifting them closed the 0.165 um gap to the supply
   router's m1 strap to 0.105 um and would *add* m1.2 errors).
2. **`nsdm.1` seams (512 in tiny decoder / ~5k in big)** - ROM cells tile at
   1.02 um pitch; one cell's transistor implant ends 0.02 um short of the
   next cell's contact implant. 0.38 um spacing required, and the gap-fill
   cannot bridge it (keepout-blocked). Fix: `rom_base_cell` now draws a small
   n+ bridge (0.54 x 0.44 um) at the top seam of every ROM cell so the
   implants merge into one shape. Scoped with an `add_implant_bridge` flag so
   the PMOS precharge cell (a `rom_base_cell` subclass) does NOT get an
   n-implant bridge (that caused 2 nsdm-over-psdm errors until scoped).

### Step 6 - full pipeline result on the fast test ROM - DONE
With all generator patches + `rom_gap_fill.sh`:

| Rule      | before patches | after (build+fill) |
|-----------|---------------|--------------------|
| everything else | 9,555 | **0** |
| m1.2      | 64            | 64 |
| LVS       | pass          | pass |
| Magic DRC | 1210          | 174 |

### Step 7 - tap-row interaction of the bridge - FOUND, FIXED
The first big-ROM rebuild with the patches came out much worse than expected:
the gap fill left 31,744 `nsdm.1` and added 7,874 each of `nsdm.2`/`psdm.1`/
`psdm.2`.

Root cause: the implant bridge (step 5) is drawn at the **top seam of every
cell**. Between normal rows the seam is 0.02 um and the bridge closes it
fully. But the array inserts a 0.52 um **well-tap band** before every 8th
row, so the seam there is 0.54 um - the bridge closes only 0.44 of it and
leaves a 0.31 um nsdm gap (< 0.38, illegal). Its fill piece then also blocks
the psdm fill inside the tap row's 0.36 um gap. The fast 64-word test ROM
never saw this because its only tap row sits at the array's bottom edge (no
cell below it).

Fix: `rom_base_array` now creates no-bridge variants of the bitcells
(`rom_base_zero_cell_nb` / `rom_base_one_cell_nb`) and uses them in the rows
directly below a tap band (`use_bridge()`); those 0.54 um gaps are legal
spacing as-is and the fill handles the tap-row psdm gap like before.

Verified on a 128-word test ROM (16 rows -> has an interior tap row, the
exact case that broke the big ROM): build + fill -> **66 errors, only
`m1.2`**, LVS pass.

### Step 8 - full rebuild of the real ROM - DONE
Rebuilt `boot_rom_2048x32` with the corrected generator (all fixes above) and
ran the fill + KLayout signoff deck on it:

| | old generator | new generator + fill |
|---|---|---|
| KLayout signoff errors | 202,793 | **74** |
| rules other than m1.2 | huge | **all 0** |
| LVS (build GDS, netgen) | pass | **pass** |
| LVS (filled GDS, fresh magic extract + netgen) | - | **pass** ("Circuits match uniquely") |
| Magic DRC (build-time) | - | 442 |

Outputs live in `boot_rom_2048x32/` (`boot_rom_2048x32.gds` = raw build,
`boot_rom_2048x32_fill.gds` = DRC-clean deliverable).

### Still to do
The remaining 74 `m1.2` are a supply-router artifact: the generic supply
router places via-stack m1 pads 0.105 um from neighbouring supply m1 shapes
(needs 0.14). Same-net shapes, so it is benign for LVS, but fixing it means
touching the generic router (shared with the SRAMs) or a net-aware m1 fill -
left as the one open item.

## 4. Files in this folder

| File | What it is |
|------|-----------|

Temporary working files (test builds, DRC reports, the dev-branch clone)
live outside this folder: `/tmp/opencode/...` and `~/OpenRAM_dev_test`.

### Generator files patched (all in `~/OpenRAM/compiler/modules/`, uncommitted)

| File | Change |
|------|--------|
| `rom_bank.py` | bitline inverter row moved down: `1.5 -> 2.0 * m1_pitch` |
| `rom_poly_tap.py` | new `extra_tap_offset` param, shifts the active-tap diffusion right |
| `rom_base_array.py` | new `tap_extra_offset` param, forwards it to the tap cells; no-bridge bitcell variants for rows below tap bands |
| `rom_decoder.py` | decode arrays created with `tap_extra_offset=0.06` (difftap.3 fix) |
| `rom_base_cell.py` | `bridge_implant_seam()`: n+ bridge across the 0.02 um tiling seam (nsdm.1 fix), flag-scoped to plain ROM bitcells |

## 5. How to run things

```bash
# everything needs the OpenRAM nix shell (provides magic, netgen, klayout)
cd ~/OpenRAM && nix develop

# regenerate the ROM (~35 min) - config lives in this folder
cd ~/pulp-asic/asic/ROM
python3 ~/OpenRAM/rom_compiler.py boot_rom_2048x32.py    # (adjust to how you ran it before)

# fast test ROM (~11 s, 64 words, used for generator-fix iteration)
python3 ~/OpenRAM/rom_compiler.py /tmp/opencode/rom_fasttest/rom_tiny_test_lvs.py

# gap fill + KLayout DRC on any ROM gds (writes <name>_fill.gds, original untouched)
bash rom_gap_fill.sh boot_rom_2048x32.gds boot_rom_2048x32
```

Nothing has been committed or pushed anywhere - all changes are local
(the one-line `rom_bank.py` fix is visible with `git -C ~/OpenRAM diff`).
